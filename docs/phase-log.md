## Interview guide

Explain the data path: a bounded provider response becomes transactional canonical rows and source mappings, SQL applies catalogue scope and aggregation, pandas fills release-year gaps, FastAPI exposes those results, and the UI visualizes them without inventing metrics. Distinguish release editions from unique recordings and catalogue representation from global popularity.

Defend the choices: partial dates avoid fabricated precision; nullable snapshots avoid invented audience data; source IDs allow repeatable upserts; savepoints isolate database tests; advisory locks survive multiple workers; batched relationships avoid N+1 queries; report caps and escaping bound work and spreadsheet/PDF interpretation. Discuss limitations honestly: bounded imports, no cross-provider identity resolution, no user accounts, no live Spotify metrics, no production-scale performance claim, and deployment configuration versus an actual live release.

## Bulk-import screen — Durable Spotify batches

Implemented `/imports`, linked in the sidebar and Workspace settings. Operators unlock with their existing ingestion token, paste artist links/URIs/IDs or upload CSV/text, review validation/deduplication and start a saved batch. The UI builds JSON automatically, caps inputs at 64 KB/100 unique artists, supports pause/resume/cancel and retry of failed entries only, shows per-item outcomes and source/profile links, and reconnects to saved batches. It stores only an opaque batch UUID in local storage, never the operator token or Spotify credentials. Ambiguous POST retries reuse a request UUID; the API returns the existing batch rather than duplicating it. The supplied two real artist links are prepared in `docs/examples/spotify-import.csv`; neither was imported from this development environment.

Added PostgreSQL batch/item tables, a nullable provider retry timestamp and cooldown indexes in migration `fc135229393e`. A worker in the API lifespan serializes queue work across API processes, shares the existing provider lock/cooldown with manual imports, persists Spotify Retry-After across restarts and uses two-minute leases for abandoned work. At-least-once recovery relies on existing source-ID upserts; completed queue entries are not restarted. Access/configuration failures pause remaining work, missing artists fail independently, and repeated rate limits are bounded before operator review. A cancelled in-flight request may still complete; completed catalogue data is not deleted. No Redis/Celery/additional hosting service is needed, but processing requires the API to be awake.

Files: `backend/app/api/bulk_imports.py`, `backend/app/services/{bulk_imports,import_control,spotify_import}.py`, model/config/lifespan/ingestion changes, the new Alembic revision and `backend/tests/test_bulk_imports.py`; `frontend/app/(workspace)/imports/page.tsx`, `frontend/components/dashboard/bulk-import.tsx`, `frontend/lib/bulk-import.ts`, navigation/settings changes and parsing/browser tests.
